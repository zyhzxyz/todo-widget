# 服务器存储与 AstrBot 接入实施计划

分支：`feature/server-astrbot`。基础修复：`faa4b18`（本地日期、计时切换、空任务列表、置顶状态）。

## 目标与边界

- 同一份个人任务、每日目标、完成记录、计时记录、清单和日记由服务器保存；桌面与 QQ 机器人通过 API 协作。
- 保留原来的纯本地模式。绝不自动上传、删除、覆盖 Windows WebView2 的数据。
- 第一版是单用户系统，不开放注册；不实现离线编辑和多主合并。
- 窗口位置/置顶/锁定/主题等设备设置仍留本机。服务器 URL 和认证信息与业务数据分开。
- 机器人只获任务与提醒权限，不获日记、完整备份和桌面管理权限。
- LLM 只解析意图、调用工具；数据库决定是否写入成功，持久化调度器决定何时提醒。

## 已核实的部署环境（2026-09-13）

宿主机 `/home/zyhzxyz/astrbot`，运行容器 `astrbot` 和 `napcat`，均为 host 网络。
两者都将宿主机 `astrbot/data` 挂载到 `/AstrBot/data`，因此同一绝对路径可用于附件交接。
现有服务只做过只读检查；不会覆盖配置、重启、安装插件或给 QQ 用户发消息作为隐式测试。

新 API 可以用独立容器、host 网络、`127.0.0.1:3210`，AstrBot 通过该地址调用。
**不同容器的 localhost 仅在上述 host 网络配置下互通。** 普通 bridge 网络应加入同一自定义网络，用服务名访问。
数据库使用单独目录（例如 `/var/lib/todo-widget`），不放 Git、不交给 Syncthing、不挂给 NapCat。
可选导出附件目录使用 `/AstrBot/data/todo-widget-exchange`，两端路径必须相同；只给该目录必要权限，不对整个 AstrBot 数据目录 chmod。

## 设计约束

### API / 数据

- Node.js 24 + TypeScript + SQLite（WAL、外键、事务），不引入 Redis。
- 清单、任务定义、按日完成记录、计时条目、日记、提醒发件箱分别存表。
- 前端兼容现有任务形状；每日目标的定义与每日完成记录在存储层分离。
- 一个递增 revision。桌面使用带预期 revision 的原子变更批次；冲突返回 409，不能用旧快照静默覆盖机器人写入。
- 每次写入带幂等键和请求摘要。响应丢失后可重试同一个操作，不能重复创建任务。
- 校验日期、长度、清单/父子引用、重复 ID、默认清单、目标范围和计时数据；导入失败全部回滚。
- 日历日期是 `YYYY-MM-DD`；真实时间保存带时区的 ISO 时间；服务器配置明确 IANA 时区，默认为 `Asia/Shanghai`。
- 不推测性地修正旧 completionDates，避免把正确记录移错一天。

### 桌面连接与迁移

- 在设置中显式连接服务器；不把原本的本地业务键当成远端缓存。
- 远端缓存与待确认写入单独存储。断网/未认证/保存中禁止新的业务写入，不能偷偷退回本地写入。
- 网络错误不宣称保存成功；允许重试同一操作、导出待保存数据。
- 并发冲突保留待保存内容，提示用户放弃并刷新或导出后手动处理；不自动最后写入胜出。
- 导出有版本的 JSON，包含四类旧数据（设备设置仅供本机恢复）；显式预检后只允许导入空服务器。
- 切回本地仍见原来的本地数据，远端数据不会覆盖它。
- 默认仅在会话保存 token；如提供记住选项，必须说明不是系统保险库。公网必须 HTTPS。

### AstrBot

- 插件适配实际安装的 Star 生命周期与工具装饰器。
- 配置独立 bot token、允许的 QQ 用户 ID、平台实例 ID；默认不启用、白名单为空即拒绝。
- 第一版仅 QQ 私聊。群聊和未经绑定的调用不能读取/写入个人任务。
- 绑定来自真实事件，不接受 LLM 指定身份/收件人。自然语言工具和普通命令执行相同权限检查。
- 至少提供查询、创建任务/每日目标、完成/撤销、设置提醒等工具；对模糊日期先询问，成功回复包含服务器确认的任务 ID 与时间。
- 不提供任意 SQL、任意 URL、任意文件访问工具。
- QQ 发送须取得 OneBot message_id；仅“找到平台”不等于送达。HTTP/QQ 异常不能 ack。

### 提醒可靠性

- SQLite 发件箱：持久化任务、租约、带随机令牌的 claim/ack/nack、次数与退避。
- 完成/删除/改期会抑制旧的未发提醒；每日目标当天完成不再提醒。
- 一次性提醒有有限补发窗口；每日提醒仅补当天，避免重启后一口气刷历史提醒。
- 无绑定不消耗发送次数。多个 worker 不能同时持有同一有效租约。
- 发送回执在插件数据目录持久化，ACK 重试不重复发送。
- 明确是至少一次投递：QQ 已收但进程在写回执前崩溃，仍可能重复；不承诺无法保证的 exactly-once。

### 安全 / 运维

- 两个独立高强度 Bearer token、恒定时间比较、请求限流、大小限制、明确 CORS、响应不缓存。
- 默认仅监听 loopback。公网放 TLS 反向代理后；不把裸 HTTP 端口直接暴露。
- `.env`、数据库及 WAL/SHM、JSON 个人备份、插件运行数据不入 Git；示例中只有占位符。
- 一致性 SQLite 在线备份及离线恢复流程，最小权限目录，健康检查。
- 对现有 AstrBot/NapCat 的安装、重启、真实账号绑定和发信必须单独确认，不能以单元测试冒充真实 QQ 验收。

## 真机验收清单

1. Windows 导出旧数据，核对任务/清单/目标/日记数量，保留离线备份。
2. 空服务器预检并导入；第二次导入应被拒绝；旧本地模式仍完整。
3. 授权 QQ 私聊创建任务，桌面轮询显示；桌面创建提醒，指定 QQ 收到并有 message_id。
4. 非白名单用户、群聊、错误平台不能读写或改提醒收件人。
5. 桌面与机器人同时修改：返回冲突而不是覆盖；网络断开只能读缓存。
6. 模拟 QQ 失败/服务重启：失败未标为已送达，恢复后重试；完成/改期后旧提醒不发。
7. 备份恢复后核对完成历史和计时记录；端口/凭据/日志无敏感信息暴露。
